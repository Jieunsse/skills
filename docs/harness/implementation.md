# 코드 작성단

작성단은 확인단에서 확정한 영향 범위 안에서 가장 작은 변경을 만든다.

## 입력과 출력

입력은 `Discovery Report`와 프로젝트 규칙이다. 출력은 `Implementation Plan`과 실제 `Change Set`이다.

## 작성 흐름

```text
작업 계획
→ 실패 조건 정의
→ 필요한 테스트·검증 기준 작성
→ 최소 구현
→ 주변 코드와 연결
→ 변경 범위 재확인
```

## 작성 원칙

- 기존 구조와 패턴을 우선 재사용한다.
- 요청되지 않은 추상화와 설정을 추가하지 않는다.
- 하나의 파일과 함수에 여러 책임을 섞지 않는다.
- 도메인 경계를 넘는 의존성을 최소화한다.
- 공개 API, 타입, 환경 변수 변경은 명시적으로 기록한다.
- 입력 검증, 권한, 보안 처리를 생략하지 않는다.
- 코드 변경에 필요한 테스트를 함께 변경한다.
- 구현과 문서가 달라지면 같은 변경에서 정리한다.

## 규칙 라벨

작성 규칙은 강도에 따라 다음 세 단계로 표시한다.

### Must

반드시 지켜야 하는 규칙이다. 위반하거나 생략하려면 작업을 멈추고 예외 사유와 대안을 기록하거나 사용자 확인을 받는다.

- 인증·권한 검증을 우회하지 않는다.
- 사용자 입력을 검증한다.
- 비밀정보를 코드와 문서에 기록하지 않는다.
- 관련 테스트와 마이그레이션을 누락하지 않는다.
- 의도하지 않은 파일을 변경하지 않는다.

### Default

특별한 이유가 없으면 적용하는 기본 규칙이다. 다른 방식을 선택하면 Implementation Plan에 사유를 기록한다.

- 기존 구조와 패턴을 재사용한다.
- 기존 상태 관리·HTTP client·도메인 경계를 유지한다.
- 코드 변경과 관련 테스트를 함께 작성한다.
- 기존 네이밍과 문서 구조를 유지한다.

### Consider

조건이 맞을 때 검토하는 선택 사항이다. 적용하지 않아도 되지만, 적용하지 않으면 위험이 생기는 경우 그 위험을 기록한다.

- 공용 컴포넌트에 Storybook을 도입한다.
- 복잡한 사용자 흐름에 e2e 테스트를 추가한다.
- 성능 병목 구간에 최적화를 적용한다.
- 대규모 모노레포에 Turborepo를 적용한다.

우선순위는 `Must > Default > Consider`다. 작성 규칙의 라벨은 검증단의 `Required · Optional`과 구분한다.

## 종료 조건

- 계획 범위 안에서 변경했다.
- 필요한 테스트와 문서를 함께 변경했다.
- 임시 코드와 디버그 코드를 제거했다.
- 공개 API·타입·환경 변수 변경을 기록했다.
- 검증단이 실행할 대상과 완료 조건이 명확하다.

프론트엔드는 가독성·예측 가능성·응집도·결합도를 기준으로 판단한다. 백엔드는 DDD 경계·인증·권한·CORS·API 계약을 중심으로 판단한다.
