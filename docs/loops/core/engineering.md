# 엔지니어링 구현 루프

엔지니어링 구현 루프는 하나의 사용자 요청을 안전하게 완료하기 위해 코드베이스 확인, 계획, 최소 구현, 검증, 피드백 반영을 반복한다.

## 적용 범위

기능 추가, 버그 수정, 리팩터링, 데이터베이스 변경, 배포 설정 변경, 문서와 설정 변경에 적용한다. 배포 순서와 업무 도구 연결은 `pipelines`에서 관리하고, 단계별 작업 기준은 `harness`에서 관리한다.

## 흐름

```text
Frame
→ Discover
→ Plan
→ Execute
→ Verify
→ Learn
→ Decide
```

## Loop Run 입력

- 사용자 요청
- 프로젝트 규칙과 문서
- 현재 코드베이스
- 관련 이슈·PR
- 성공 기준과 비목표

하나의 `Loop Run`은 커밋이나 PR과 반드시 일치하지 않는다. 필요하면 여러 커밋과 작업 단위를 포함한다.

## 시작 트리거

성공 기준과 비목표가 정해진 코드·문서·설정 변경 요청이 들어오면 시작한다. 문제나 수용 기준이 불명확하면 문제 정의 또는 제품 기획 Loop로 먼저 되돌린다.

## Step 0. Frame

요청을 실행 가능한 작업으로 정의한다.

```text
작업 목표
성공 기준
비목표
초기 위험
```

성공 기준이 없으면 다음 단계로 넘어가지 않는다.

## Step 1. Discover

코드베이스 확인단을 수행한다.

- 프로젝트 지침과 관련 문서 확인
- 디렉터리·모듈·도메인 경계 확인
- 진입점과 호출 흐름 확인
- API·데이터·상태 흐름 확인
- 기존 테스트와 실행 명령 확인
- 최근 변경과 현재 작업 트리 확인
- 영향받는 파일과 변경하지 않을 영역 확인

산출물은 `Discovery Report`다.

```text
영향받는 파일·모듈
변경하지 않을 영역
재사용할 구현
위험 요소
미결정 사항
검증 계획 초안
```

## Step 2. Plan

변경 순서와 완료 조건을 정의한다.

산출물은 `Implementation Plan`이다.

```text
파일별 변경 계획
변경 순서
테스트 계획
문서 계획
보안·데이터 영향
완료 조건
```

작성 규칙은 다음 라벨을 사용한다.

```text
Must     반드시 준수
Default  특별한 이유가 없으면 적용
Consider 조건이 맞을 때 검토
```

`Must` 규칙을 위반하거나 생략하려면 작업을 멈추고 예외 사유와 대안을 기록하거나 사용자 확인을 받는다. `Default`를 변경하면 계획에 사유를 기록한다. `Consider`는 적용하지 않아도 되지만 위험이 생기면 잔여 위험을 기록한다.

## Step 3. Execute

독립적으로 확인할 수 있는 작은 변경 단위로 구현한다.

```text
작은 변경
→ 관련 테스트
→ 로컬 검증
→ 다음 변경
```

다음 상황이 발생하면 계획을 갱신하고 영향 범위를 다시 확인한다.

- 예상하지 못한 모듈 영향
- 새로운 외부 의존성
- API 계약 변경
- 데이터 마이그레이션 필요
- 보안 경계 변경
- 기존 구조와의 충돌

산출물은 실제 `Change Set`이다.

## Step 4. Verify

검증단을 실행한다.

```text
포맷·정적 분석
→ 타입·컴파일
→ 관련 단위 테스트
→ 빌드·패키징
→ diff 검토
→ 문서·환경·보안 검토
```

변경 유형에 따라 계약·통합·e2e·마이그레이션·접근성 검증을 필수로 승격한다. 결과는 실행 명령, 대상 범위, 결과, 미실행 검증, 실패 원인, 잔여 위험을 포함한 `Verification Report`로 기록한다.

## Step 5. Learn

검증 결과와 리뷰 피드백을 분류한다.

```text
요구사항 문제
설계 문제
구현 문제
테스트 문제
환경 문제
```

| 문제 | 복귀 단계 |
| --- | --- |
| 요구사항이 잘못됨 | `Frame` |
| 영향 범위나 구조가 잘못됨 | `Discover` |
| 구현 방향이 잘못됨 | `Plan` |
| 코드 오류 | `Execute` |
| 검증 방법이 부족함 | `Verify` |

## Step 6. Decide

```text
Continue  다음 변경 단위 진행
Revise    이전 단계로 돌아가 수정
Block     외부 정보·권한·환경 대기
Stop      목표 달성 또는 반복 가치 부족
```

`Consider` 수준의 개선만으로 무한 반복하지 않는다. 추가 반복의 기대 효과가 비용과 위험보다 낮으면 종료한다.

```text
Engineering Implementation Loop
└── Harness Run
    ├── Discovery
    ├── Implementation
    └── Verification
```

## 완료 조건

- 성공 기준을 충족한다.
- `Must` 규칙 위반이 없다.
- 필수 검증을 통과한다.
- 필요한 선택 검증을 수행했다.
- 잔여 위험을 기록했다.
- 관련 문서가 구현과 일치한다.
- 추가 변경의 기대 효과가 낮거나 없다.

다음은 완료로 처리하지 않는다.

- 검증을 실행하지 못했지만 사유를 기록하지 않은 경우
- 보안·권한 검증을 생략한 경우
- 데이터 마이그레이션을 검증하지 않은 경우
- 요구사항이 여전히 모호한 경우
- 계획보다 범위가 커졌지만 재검토하지 않은 경우

## 계층별 적용

### 프론트엔드

```text
UI 요구사항
→ 화면·상태·API 흐름 확인
→ 컴포넌트 계획
→ 구현
→ lint·typecheck·test·build
→ 필요 시 Storybook·e2e
```

로딩·성공·빈 상태·에러 상태, 폼 검증, 접근성, 반응형 동작, API 실패 처리를 확인한다.

### 백엔드

```text
API 요구사항
→ 도메인·권한·데이터 흐름 확인
→ DDD 경계 계획
→ 구현
→ 단위·통합·계약 테스트
→ 마이그레이션·보안 검증
```

JWT 인증·권한, validation, CORS, 트랜잭션, JPA 쿼리, Flyway 마이그레이션, API 문서와 실제 응답의 일치를 확인한다.

## Git·PR과의 경계

이 루프는 변경·검증·피드백을 관리한다. GitHub Issues, Linear, 브랜치, PR, CI, 배포 연결은 `pipelines`에서 관리한다. 단, Loop Run 문서에는 관련 이슈와 PR 링크를 남긴다.

관련 하네스는 `docs/harness/discovery.md`, `docs/harness/implementation.md`, `docs/harness/verification.md`다.
